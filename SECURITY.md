# Security

## Reporting

Open an issue at https://github.com/youssefsiam38/kotaemon-railway/issues for a problem with the
wrapper. Report anything in the application itself to https://github.com/Cinnamon/kotaemon. Do not
include credentials, tokens or public hostnames in an issue.

## The central fact

kotaemon creates its first administrator for you, and by default the password is `admin`.

`flowsettings.py`:

```python
KH_FEATURE_USER_MANAGEMENT_ADMIN = str(config("KH_FEATURE_USER_MANAGEMENT_ADMIN", default="admin"))
KH_FEATURE_USER_MANAGEMENT_PASSWORD = str(config("KH_FEATURE_USER_MANAGEMENT_PASSWORD", default="admin"))
```

Upstream's README documents it: "Default username and password are both `admin`." That is fine for
something you run on your laptop and a serious problem on a public hostname, which is what a hosting
platform gives every service.

It is also a one-shot decision. `create_user` returns early when the username already exists, so the
password variable is read on the boot that creates the account and ignored afterwards. A deployer
who notices later cannot fix it from the environment; they have to sign in with the password that is
already published and change it in the interface. The template's job is to make sure that moment
never happens, so the wrapper refuses to start without a real password.

`tests/smoke.sh` asserts this directly against the application's own database: exactly one account
exists, the supplied password's SHA-256 matches it, and the hash of `admin` matches nothing.

## Settings this wrapper refuses

Each of these removes the login. None has a safe meaning on a public URL, so the container exits
rather than warning.

| Setting | What it does |
|---|---|
| `KH_FEATURE_USER_MANAGEMENT=false` | Turns accounts off entirely. Every tab becomes visible to everyone. |
| `KH_DEMO_MODE=true` | Launches upstream's public demo application, which sets user management to false. |
| `KH_GRADIO_SHARE=true` | Asks Gradio to publish a `*.gradio.live` tunnel straight to the container. That URL bypasses the platform, and nothing this template does can protect it. |
| `KH_SSO_ENABLED=true` | Starts a different application, `sso_app.py`, whose identity provider this template does not configure. |

## What the login does and does not cover

kotaemon gates its interface by **visibility**: `toggle_login_visibility` in `libs/ktem/ktem/main.py`
shows the chat, file and resource tabs only once a session holds a `user_id`. That is a client-side
consequence of server-side state, not an HTTP-layer check on each request, so two things follow.

First, **the interface definition is public**. Gradio serves the whole Blocks tree to every visitor,
so the names of every tab and control are in the page whether or not anyone has signed in. Labels,
not data. `tests/smoke.sh` asserts this rather than pretending otherwise.

Second, the event endpoints exist whether or not a caller has signed in. In practice a caller
without a session gets the default state, which is `None` when user management is on, and the
handlers that matter do their work against that user; an unauthenticated event call is refused, and
a test asserts that too. This wrapper does not change any of it, and it is worth knowing about if
your corpus is sensitive:

- Put the service behind Railway's own access controls, or on a private network, if the documents
  are confidential.
- Treat accounts as a way to separate colleagues, not as a hard boundary against an attacker.

The alternative, a shared password in front of the whole application, was considered and rejected:
it would make every colleague share one credential *and* hold their own, which defeats the reason to
run a multi-user product.

## Passwords at rest

kotaemon stores a bare, unsalted SHA-256 of each password, in
`libs/ktem/ktem/pages/resources/user.py`:

```python
hashed_password = hashlib.sha256(pwd.encode()).hexdigest()
```

That is weaker than a password-hashing function like bcrypt or argon2: identical passwords produce
identical hashes, and a stolen database is cheap to attack offline. The wrapper cannot change it
without patching the application, so instead it insists on at least twelve characters, and the
template generates twenty-four random ones rather than letting anyone choose.

## Secrets

- `KOTAEMON_ADMIN_PASSWORD` is generated by the template with `${{secret(24)}}` and is never printed
  by the wrapper. The start-up log reports the username and the password's length, nothing more.
- Model-provider keys such as `OPENAI_API_KEY` are passed straight to the application and are not
  logged. They are also stored in the application's settings once entered through the interface.
- Nothing is baked into the image at build time. There are no credentials in the Dockerfile, in a
  build argument, or in any layer.

## Transport

Railway terminates TLS at its edge and the certificate covers the generated domain. Plain HTTP
redirects to HTTPS.

## Third-party calls made by the application

Whatever model provider you configure: answers and the text being asked about are sent to it. That
is the point of the product, and it is the one place your documents leave the instance. Embedding
models are downloaded from Hugging Face on first use. Gradio's own analytics are disabled in the
image.

## Updates

The upstream image is pinned by digest. A version bump is a pull request that changes the digest, is
tested by CI against the real image, and is released as a new wrapper tag. See `MAINTENANCE.md`.
